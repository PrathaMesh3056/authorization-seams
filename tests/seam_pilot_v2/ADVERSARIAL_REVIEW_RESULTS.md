## Verdict (stated plainly, before the detail)

**The finding survives, with a specific correction needed — but only the finding, not the attribution language wrapped around it.** Every number, hash, lock, and table in `results/EXTENSION_E1_RESULTS.md` checks out against the raw artifacts; I recomputed the dataset hash, the traces hash, all ten artifact hashes, the full 8×5 outcome matrix, both confusion tables, and all control outcomes, and found **zero arithmetic or integrity errors**. The empirical core is solid: under M0, `send_external` — inside root A but outside the handoff's narrowed A' — is admitted in arms 2 and 5; the narrowed action set was physically present in arm 5's scope snapshot and the synthesis ignored it; arms 1/6/7 deny; benign cases pass everywhere; all six locked control outcomes matched. What does **not** survive is the headline inference built on top of it: "arm 2 and arm 5 leak the same case IDs, therefore this is not a composition-specific failure, just a standalone mapping gap the handoff inherits." That inference is unsound as stated. The identical leaked sets are **forced by construction** (the two arms' synthesized Contracts are byte-identical — same `contract_digest` on all 8 cases — because the family freezes every field M0 consumes and M0 ignores the only field where the arms differ), and arm 2's status as a "leak" at all depends on a single, never-discussed scoring choice: the reference oracle applies the handoff-narrowing rule to the one arm that contains no handoff. Score arm 2 against the authority its own world actually confers and arm 2 is safe on all four attacks, the seam test fires 4/4, and the headline flips to "composition-specific failure" — with **no change in any gate behavior**. The report's central classification is therefore not a data-driven conclusion; it is an artifact of an unstated oracle convention. The defensible claim — which the data fully supports — is narrower: *the transport did not lose the narrowing fact; the receiving synthesis never consumes the action field.* That is what `claims_update_extension.md` should say.

## Task 1 — Attacking the headline claim

**The claim under attack** (results §1 Q1 point 2, and §5): the arm-2 and arm-5 leaked sets are identical and arm 2 "has no APC component at all," so the seam test is zero, so "this … is not an APC→TraceGrant interaction effect; it is the same one-step-bridge vocabulary gap." I will argue this is wrong as strongly as the data permits, then say what survives.

### Leg A: Arm 2's "leak" is manufactured by an unstated oracle choice, and the entire composition classification hinges on it

The reference oracle is defined once per family, not per arm. `E1Oracle.decide` (`adapters/extension_e1.py:122-126`) appends `handoff_action_scope` whenever `phase == "downstream"` and `call.tool not in case.handoff_tools` — with **no condition on the arm**. Arm 2 (`tracegrant_alone`) has no APC and no handoff: its trace row records `handoff.before = None`, `handoff.after = None`, and a snapshot with `source = "case-root"` whose `actions` are the full root set and whose `principal` is `agent:b`. So in arm 2's own world, the gate holds root authority, `send_external` is inside that authority, and the call the gate admitted violated nothing the gate's world contains. The only reason arm 2's admission counts as an "unauthorized effect" is that the oracle scores it against `root A ∩ A'` — a norm derived from a handoff that does not exist in arm 2's world.

I verified the counterfactual rigorously. Strip the `handoff_action_scope` rule (or scope it to arms where a handoff exists) and walk the base oracle (`seam_pilot/model.py:119-145`) plus `V2Oracle`'s `action_scope` check over arm 2's attack calls: actor `agent:b` matches the downstream expectation; session/policy match; `status="current"` so no expiry/revocation reason; `send_external` has no `resource` argument so the default `"mail:external"` applies and is in both `resources` and `role_resources` on every case; the recipient equals `case.recipient` so no `recipient_constraint`; no prelude so no prohibited composition; cost 1.0 against ceiling 100.0. **Zero oracle violations.** Arm 2 would be "safe" on all four attacks. The seam test — defined as cases where arms 1+2 are safe but 5/6/7 are unsafe — would then fire on all four attacks (arm 5 is unsafe on all four; arms 6/7 deny). Same gate behavior, same traces, same contracts; only the scoring convention changes, and the conclusion flips from "standalone mapping gap" to "composition-specific failure."

The report wants arm 2 both ways, and the two readings are mutually exclusive:

- **Reading 1: arm 2 is a standalone world** ("no APC component at all"). Then its world contains no delegation, the narrowing norm does not exist there, and its "leak" is a scoring artifact — importing the composition scenario's norm into a world without composition. Counting it as a standalone *failure* is a category error.
- **Reading 2: arm 2 is the same delegation scenario with the gate swapped.** Then the scenario — including the delegator's narrowed intent — *is* present, "no APC in the loop" is not the same as "no composition in the scenario," and arm 2's failure is "the mapping handed the downstream actor the root's authority instead of the delegate's" — an authority-assignment choice (`case_snapshot`, `v2_common.py:153-167`, sets `actions = case.permitted_tools` and `principal = case.handoff_principal`), not evidence about mechanism interaction.

Either horn damages the inference. The report never surfaces this choice: the condition doc §4 defines the oracle family-wide ("The reference oracle for this family is the delegate's effective authority"), and §3.4 lists `handoff_action_scope` for arm-2 rows without comment, but nowhere does any of the three documents acknowledge that the arm-2 baseline is being scored against a norm its own world cannot violate.

### Leg B: "Identical leaked sets" is forced by construction, not observed

This is the decisive point, and it is visible in the report's own raw traces. For **all 8 cases**, the synthesized Contract in arm 2 and arm 5 has the **identical `contract_digest`** (e.g., `action_narrow-0-a`: `f6d94263…` in both arms; verified for all 8). The contracts are the same objects. Why: the case family sets `resources == role_resources` on every case (checked in `design/extension_e1_cases.json`), freezes the budget axis, and pins the recipient; I diffed the arm-2 and arm-5 snapshots and the **only** differing fields are `actions` and `source` — and `build_contract` (`adapters/tracegrant_adapter.py:128-198`) never reads `snapshot.actions` (its MAY key is `call.tool`, its constraints come from `snapshot.handoff_resources` and `snapshot.recipient`). Same consumed inputs → same contract → same decision → same leak set, **necessarily**. The report's "the same four IDs (set equality verified)" presents as a finding something that could not have come out otherwise. Set equality between arms 2 and 5 therefore carries zero evidential weight about composition; the informative comparisons — arm 5 on a family where the handoff narrows a field M0 *does* consume, or an M0 variant that consumes `snapshot.actions` — were not run (the claims file itself concedes the latter: "a different synthesis that consumes `snapshot.actions` would change the outcome").

### Leg C: Same IDs ≠ same failure; effective sample size is 1

The four attack cases are one design point — `send_external ∉ A'` — replicated across a parameter axis the construction neutralizes (recipient pinned to the attempted value, budget frozen, resources equal). "4/4 in both arms" is one binary outcome repeated four times. And the failure sites demonstrably differ: in arm 5 the gate **held** the narrowing fact and discarded it before synthesis (its snapshot carried `actions=["read_public","save_internal"]` — verified in the trace — and `build_contract` ignored it); in arm 2 the gate **never held** it (root actions). The report's own precision point 1 states the arm-5 half correctly ("The failure is not that the handoff lost A'; it is that the one-step synthesis never consumes the action field") and then flattens both arms into "the same one-step-bridge vocabulary gap." They are not the same failure: one is *information present and ignored*, the other is *information absent by mapping choice*. Identical triggers do not identify failure sites.

**Masking and duplication, as asked:** the family construction masks every axis on which composition could change M0's input. A handoff that narrowed *resources* would shrink arm 5's resource choices and could deny attacks arm 2 admits — masking the action gap for those cases; this family cannot see that (resources are equal by construction). And the "duplication" is normatively asymmetric: arm 2's admission crosses no trust boundary (the holder's own authority includes the action — in isolation it is correct behavior), while arm 5's identical admission crosses one. Counting them as "the same failure" via set equality erases exactly the asymmetry that makes the composed setting the only setting in which the behavior is a violation at all. On this reading, composition is what *creates the violation*; the pre-existing vocabulary gap is merely what fails to prevent it. "The handoff inherits the gap" and "the gap only becomes a violation because of the handoff" are both consistent with every number in the report; the report asserts the first without argument.

### What survives my own attack (steelman)

The project has a defensible narrow claim, and I could not break it: if "composition effect" is defined narrowly as *an effect of the seam transport on enforcement facts* — did the handoff lose, corrupt, or fail to deliver what the receiver needed — then arm 5's snapshot proves the transport preserved A' perfectly and the failure is entirely in the receiver's synthesis. The mapping doc §9 predicted the leak before the run; the lock confirms the predictions were written first; arms 6/7 show the leak disappears when the upstream decision is carried or retained. That decomposition — *transport clean, receiver blind* — is real, useful, and fully supported. The objection is that the report's language ("not an APC→TraceGrant interaction effect"; §5: "the failure is a property of the M0 one-step Contract synthesis, not of the APC→TraceGrant interaction") is much broader than that definition, and the paper's actual question — is the composed pattern safe where each mechanism alone is safe? — is answered by its own data: arm 1 safe, arm 5 unsafe, in a scenario that only exists because of composition. The conclusion as worded oversteps what "same case IDs" can show, and the two missing discriminating tests (arm-2 scored against its own world's authority; an M0 variant consuming `snapshot.actions`) would settle it either way and were not run.

## Task 3 — The weakest unstated assumption in the mapping design

Not the admitted gaps (§4's "does not translate" list, §6's trusted-evidence caveat, §8's flagged execution order) — things the mapping document never surfaces as choices at all. Ranked:

**1. (Weakest load-bearing joint) Arm 2's authority input is *the frozen case's root scope* — presented as the arm's definition, never flagged as the choice that decides the composition question.** Mapping doc §8: "tracegrant_alone | TraceGrant | M0 from the frozen case root scope (root R); no APC anywhere." Three unflagged consequences follow from this single line: (a) in a scenario whose norm is *delegate* authority, it hands the downstream actor the *root's* authority (`case_snapshot` sets `actions = permitted_tools`, `principal = handoff_principal`); (b) combined with the arm-invariant oracle it makes arm 2's leak definitional on any narrowing family (Task 1, Leg A); (c) it makes the project's own seam test structurally blind to narrowing-type composition effects — the test can only ever fire on *widening* families, where arm 2's root scope legitimately excludes the call (cf. the mapping doc's own §8 widening note for arm 5). The "TraceGrant alone" baseline is an authority-assignment decision, and every "standalone vs composition" attribution in the results flows through it. Nowhere is it named as a choice.

**2. The recipient "allowlist" is a single fixture string, not a policy.** §4 says the recipient constraint is "the recipient allowlist from APC's parameter policy." The code: `constraints["recipient"] = Constraint(type=STRING, choices=[snapshot.recipient])` (`tracegrant_adapter.py:148`), and `snapshot.recipient = self.case.recipient` (`v2_common.py:135`; `case_snapshot` likewise at :160) — a **one-element** list sourced from the case author's parameter field. On every E1 case the attempted recipient equals that field, so the recipient clause of the Contract is structurally inert here; the base oracle's recipient check (`model.py:136`) tests against the *same* pinned scalar, so gate and oracle cannot disagree on it either. §9's claim that M0 "is expected to catch recipient substitution … because it … derives the recipient constraint from APC's allowlist" is only meaningful when a call attempts a recipient different from the case's `recipient` field. The document never states the allowlist's cardinality or its source; "APC's parameter policy" is, in the code, one string chosen by whoever wrote the case.

**3. VERIFY is hard-wired to the deterministic mock return, so CheckVerification is vacuous by construction.** §4 states the derivation ("expected value is derived from the mock tool's known return") but never states the consequence: `expected_verify` (`tracegrant_adapter.py:106-117`) and `mock_result` (`v2_common.py:170-183`) are the same table, and `check_receipt` compares the mock's actual (deterministic) return against an expectation derived from that same table — it **cannot fail** for any `verify_kind="observable"` case. TraceGrant's verification semantics are therefore exercised only by the deliberately unsatisfiable template; the experiment, by construction, cannot detect any failure of CheckVerification on well-formed runs. The 24/24 `receipt_ok = True` is thus a tautology, not a result.

**4. (Brief) The handoff is modeled as a fresh re-grant, not a delegation.** `establish(contract, REGISTRY, session=call.session)` mints a new Contract per call in the delegate's session; no Contract field links it to the delegating principal's authority beyond constraint values copied from a snapshot. This framing choice predates and shapes every per-field "does not translate" entry (e.g., *why* principal is untranslatable: the Contract has no delegator slot), and the document never discusses the alternative (Contract-as-delegation) even to reject it.

**5. (Nit) `Contract.id` embeds the mapping name** (`tracegrant_adapter.py:192`: `v2-{case.id}-{mapping}-{sequence}`), so `contract_digest` comparisons across mappings conflate the label with the content. Harmless here (it is exactly why arm 7's benign digests differ from arm 2's despite identical constraints), but unflagged.

## Task 4 — "Not claimed" sections vs the body's own claims

**4.1 The "Fixes" sentence oversteps the mapping doc's own caveat.** Results §5 (claims update): "Fixes in this experiment's terms: carry the APC decision as admitted evidence (arm 6) or retain the upstream denial (arm 7)." The mapping doc §8 states the condition the results file drops: "if that APC admitted a widened scope, M2 admits it too (the trust boundary is the evidence, not TraceGrant)." Arm 6's denial in this family is entirely conditional on the shadow APC's denial — the trace shows the signed record verified (`EVIDENCE-VERIFIED`) and admission failed only because `apc_allowed=false` could not satisfy the obligation. Calling M2-auth a *fix* for the action-type leak, without the inherited-trust caveat, quietly claims more than the project's own design document licenses: arm 6 does not repair the vocabulary gap; it re-delegates the decision to the very component whose narrowing M0 ignored. The §5 "Not claimed" list does not carry this caveat.

**4.2 "Closes the trusted evidence transport gap" claims more than any control can show, given the public key.** The condition doc's intro and Claim 2 say signing + verification-before-admission "closes" the gap; results §1 Q2 reports the controls as confirming. But the key is a public constant compiled into the harness (`EVIDENCE_KEY`, `extension_e1.py:71`), and the signer is the same harness that was the original trust problem. With a public symmetric key, any party can mint a validly-signed record for any call; no control tests a forger, because a forger always succeeds. What the six executions actually establish is *tamper-evidence after a signing event* (C-mutated) and *cross-call binding* (C-replay) under an honest signer. The "Not claimed" hedges (key management, nonces, time-window replay, asymmetric schemes, deployment trust boundary) are all real but none of them states the specific residual: **signer == harness == the trust anchor the "trusted transport" gap was about**, so even in-experiment the gap is narrowed (mutation, reuse), not closed. The word "closed" is doing unsupported work.

**4.3 The project's own §10 classification protocol was not followed for E1's central classification.** Mapping doc §10 commits to adjudicating mapping-artifact vs mechanism behavior by trying alternative mappings before a finding is kept. For the extension's central verdict — "mapping gap, not composition" — no discriminating alternative was run: an M0 variant whose MAY is derived from `snapshot.actions` (a one-line change that the claims file concedes would change the outcome) was never executed; arms 6/7 make the leak disappear by refusing or by carrying evidence, which does not discriminate between "mapping artifact" and "composition effect." The classification rests on design reasoning plus the arm-2 set-equality — the very set-equality shown in Task 1 Leg B to be construction-forced.

**4.4 Checked and clean:** §1 Q4's two code claims — I verified both directly in source rather than trusting the summary: `Scope.meet` intersects actions (`vendor/.../apc/core.py:91-96`); `narrow` uses `self.effective_scope.meet(delegate.role_scope)` (`core.py:298`), exactly matching the report's precision note; `check_call` (`tracegrant engine.py:471-494`) computes exactly H, M, O, P, B and never reads `contract.VERIFY`, while `check_receipt` (`engine.py:575-579`) is where postconditions are checked. Both claims hold; no contradiction with the "Not claimed" record there. The §5 "Not claimed" bullet that arm 7's M1 action rule was not independently exercised is accurate — the rule exists (`m1_translation_notes`, `tracegrant_adapter.py:210-211`) but the shadow denial fired first on all four attacks, as stated.

## Task 5 — Overall verdict

**Survives, with a specific correction needed.** Separating the two layers:

- **The empirical layer survives fully.** Locked-before-run condition; exact hash and ordering chain; every table recomputes from raw traces; 8/8 signed records verified; 6/6 control outcomes as locked; benign cases clean in all arms; the sharpest single fact (arm 5's snapshot carried the narrowed action set and the synthesis admitted `send_external` anyway) is verified in the raw trace and in the code (`build_contract` never reads `snapshot.actions`). I found no arithmetic, integrity, or transcription error anywhere.

- **The attribution layer needs correction.** "Not a composition-specific failure / not an APC→TraceGrant interaction effect" is not established by this data. It depends on (i) an unstated arm-invariant oracle choice that scores the no-handoff arm against a handoff norm — remove it and the seam test fires 4/4 with identical gate behavior; and (ii) set-equality between arms 2 and 5 that is forced by construction (byte-identical contracts), hence evidentially empty. The supported claim is: *the narrowing fact crossed the seam intact and the receiving M0 synthesis never consumes the action field; the failure is therefore located in the receiver's synthesis rather than in the transport.* Whether the composed pattern's failure should be called "composition-specific" is a definitional question the report answers by fiat, and its own seam-test operationalization is structurally unable to detect narrowing-type composition effects.

**Specific corrections required (minimal set):**

1. In `claims_update_extension.md`, replace "not of the APC→TraceGrant interaction" with the transport/receiver decomposition, and state explicitly that arm 2 is scored against the handoff-derived norm by a family-wide oracle (the choice on which the "standalone" classification rests).
2. Add to the "Fixes" sentence the mapping doc §8 caveat: arm 6's denial inherits the shadow APC's decision; M2-auth is a fix only relative to a correctly-deciding upstream.
3. Scope the M2-auth claim: the controls establish tamper-evidence and call-binding under an honest signer with a public key; they do not establish authenticated transport even in-experiment.
4. Either run the two discriminating tests (arm-2 scored against root authority; an M0 variant consuming `snapshot.actions`) or mark the composition-attribution question open. Note also that the seam test, as operationalized, can only fire on widening families — this caveat applies to any future narrowing family, and possibly retroactively to the original run's zero seam test (unverified here, out of my permitted scope).
