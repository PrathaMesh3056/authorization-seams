**Is the new signature family the first H5 end-to-end test, and what does it show?** It is H5's first end-to-end test, and it splits the claim:

- **Verification without the key is impossible — confirmed.** A token whose content would pass (T0 scope) but which is signed with the prototype's published key constant instead of the trusted harness key is rejected `SIGNATURE_INVALID` in every token arm (`foreign_key_signed` ×4 ×4 arms; controls S2-foreign, S1-failure, S2-mutated). Without the key, the check's only behavior toward such a token is rejection.
- **Verification does not attest the signer — refined.** Two tokens with identical content, one attributed to the bridge and one to a delegate, produce identical check results (control S2-two-minters: `ALLOWED by scope:read_confidential` / `OUTPUT_ALLOWED` for both). In the matrix, delegate-minted tokens are admitted exactly like bridge tokens in every arm that does not restore the prior authorization (`keyholder_plain` admitted 4/4 in all four arms; `keyholder_widen` admitted 4/4 in arms 2/5). The check verifies *possession of the key* and payload integrity, not which keyholder minted the token. A cross-mechanism bridge holding the key is, to the receiver, indistinguishable from the DAS itself, and the receiver's authorization is exactly the manifest of the presented token.
- **The "or a call to the DAS" path was not exercised end-to-end.** The pinned prototype's check function is DAS-side code; the matrix registers each token with a fresh `DelegationAuthorityService` and calls the native checks. There is no live DAS network service in the prototype to call.

## 2. The finding (third occurrence): the seam subtracts, it does not add

Across three seam pilots — the APC→TraceGrant 80×7 run, its action-narrow extension E1, and this APC→SentinelAgent 96×7 run — every unauthorized effect observed under composition was already present with the receiving mechanism alone, and the composed arms produced no new failure. In this run the arm-2 and arm-5 leak sets are **identical** (28/28 cases, same ids; self-review `arm2_arm5_identical_leak_sets` pass), and every one of the 28 leaked cases is an attack the mechanism-alone arm 2 already admitted (0 false negatives anywhere, 0 false positives against the locked predictions).

This is the paper's actual finding, stated as narrowly as the data allows:

> Under the frozen family-wide oracle (the scoring convention locked for these runs), in every pair we have built and run, the failures of a cross-mechanism handoff are **subtractive**: the seam carries less context than the receiving mechanism's checks would need to detect standing authority violations on their own, and the composition creates no authorization failure that one of the mechanisms does not already exhibit standalone. The seam changes *which decisions are reachable*, not *which effects are possible* under that convention. The convention has one measured exception: under arm-native scoring E1's action-narrow seam test fires 4/4 (`paper\CONSOLIDATED_CLAIMS.md` ★/§4.2). The mechanism-specific failure faces are the vocabulary gaps of the receiver (unrepresentable state: absolute and relative time, revocation, principal identity, composition history, cumulative budget, replay), and they repeat across different receiving mechanisms.

What the seam *does* change in this pair: the composed arms can only close those gaps by carrying the upstream decision (arm 6: 28→0 leaks via a signature-verified APC attestation) or by refusing untranslatable cases (arm 7: 0 leaks, 20 benign cases refused). Those are remediation mechanics, not new failures.

## 4. Method (one paragraph; details in the design documents)

The bridge represents the handoff in SentinelAgent's own vocabulary: T0 mints one per-delegation-hop DelegationToken per attempted call (scope = tool, manifest = the canonical method+endpoint strings derived from the handoff snapshot, output tags = the tool's standard tag), and the receiving side runs the pinned prototype's own `check_api_call` / `check_output` / `verify_signature` code paths against a `DelegationAuthorityService` with the token registered. The module-level key constant is set to the harness bridge key at runtime (`install_bridge_key`), which models the trust relationship without editing the upstream file. Arms 1/3/4 execute through the frozen v2 runner verbatim; arms 5/6/7 add the shadow APC first (recorded, not propagated / carried as a signed attestation / fail-closed with T1 refusals). The test key is `seam-pilot-sentinelagent-bridge-test-key-2026`; the foreign-key probes use the prototype's published constant. `c1a`'s root-intersection requirement is met by construction (T0's manifest is APC's post-handoff effective scope). P2 (intent-NLI) is out of scope: the token's `intent_text` is carried, not classified (see the mapping doc §7; no case family was invented for it).

## 7. Signature family (new; H5's first end-to-end test)

Two pairs on the document axis; the presented token is a case-declared input to the receiving gate, not bridge-synthesized:

- `foreign_key_signed` (attack, aspect `signer_key`): honest T0 content re-signed with the prototype's published key constant. Predicted safe.
- `trusted_key_signed` (benign, aspect `signer_key`): the same content signed with the trusted harness key. Predicted safe.
- `keyholder_widen` (attack, aspect `mint_provenance`): a delegate-minted token whose manifest the caller writes, containing the widened resource. Predicted unsafe.
- `keyholder_plain` (benign, aspect `mint_provenance`): a delegate-minted token for an ordinary call. Predicted safe.

| template | kind | arm 2 T0 | arm 5 T0 | arm 6 T2-attest | arm 7 T1 |
|---|---|---|---|---|---|
| foreign_key_signed | attack | SIGNATURE_INVALID x4, leaks 0 | SIGNATURE_INVALID x4, leaks 0 | SIGNATURE_INVALID x4, leaks 0 | SIGNATURE_INVALID x4, leaks 0 |
| trusted_key_signed | benign | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 |
| keyholder_widen | attack | ADMITTED x4, leaks 4 | ADMITTED x4, leaks 4 | APC-DENY x4, leaks 0 | SHADOW-DENY x4, leaks 0 |
| keyholder_plain | benign | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 |

Reading: a different **key** is always noticed (`SIGNATURE_INVALID`, 4/4 in all four token arms, and never counted as a false denial — a correctly rejected unverifiable token is not an FD by the locked scoring rule). A different **minter with the same key** is never noticed: `keyholder_plain` is admitted everywhere; `keyholder_widen` is admitted in arms 2/5 exactly as a bridge token would be, and is stopped only by the prior authorization being restored (arm 6, `APC-DENY` via the attestation) or by the shadow denial (arm 7). The delegate does not need any authority under the token's vocabulary — it needs the key.

The signature family adds one leak class to the pair (`keyholder_widen`, 4 cases in arms 2/5) that is a token-ecosystem property, testable with the mechanism alone (arm 2 admits it). It remains a standalone gap, consistent with §2.

## 8. Freshness family: an expired token passes P6/P7

Locked prediction (condition doc §5): the synthesized token for an expired-status case still passes P6/P7 in **every arm that adds no expiry check**; no arm in this design adds a token-expiry check; the only expiry handling is arm 6's attestation freshness requirement (which reads the *APC* state, not the token) and arm 7's dynamic-state refusal.

| template | kind | arm 2 T0 | arm 5 T0 | arm 6 T2-attest | arm 7 T1 |
|---|---|---|---|---|---|
| expired_delegation | attack | ADMITTED x4, leaks 4 | ADMITTED x4, leaks 4 | APC-DENY x4, leaks 0 | SHADOW-DENY x4, leaks 0 |
| expired_delegation | benign | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 | ADMITTED x4, leaks 0 | T1-REFUSE:dynamic_state_untranslated x4, leaks 0 |

Observed: the expired token is admitted in the two arms under test (arms 2/5, 4/4 attacks, 4 leak events) — the native checks never look at `expiry` (control S1-valid executes the same fact in isolation: a 2001-dated token returns `ALLOWED by scope` / `OUTPUT_ALLOWED`). Arm 6 denies `APC-DENY` because the carried APC state says the delegation is expired; arm 7 refuses the case as untranslatable dynamic state. The prediction held in every arm; the control S1-failure (mutation after signing → `SIGNATURE_INVALID`) and S1-probe (revoked via `revoke_chain` → `TOKEN_REVOKED`) show the checks are not blanket no-ops.

## 9. Arm 6 (`apc_sentinelagent_retained`): the APC decision as signed evidence

The shadow APC decision and the pre-admission snapshot are carried as a real DelegationToken (scope `apc-attestation`) whose `intent_text` is the canonical JSON of the 12-field evidence record from the reused `shadow_evidence_values`, verified through the prototype's own `verify_signature()`. Gate order (locked): attestation present → signature → payload parse → binding (tool/resource/recipient/task/principal against the attempted call and the pre-admission snapshot) → `apc_allowed` → budget → freshness → revoked → composition → native P6/P7 on the presented scope token.

Observed codes: {"ADMITTED": 62, "APC-DENY": 42, "SIGNATURE_INVALID": 4}. Zero leaks and zero false denials; all 28 leak-class attacks are denied as `APC-DENY` with the shadow APC's reasons. Special cases: the four `foreign_key_signed` attacks are denied on the **presented token's** signature (the attestation itself is valid); the four `unsatisfiable_verify` attacks are **admitted** (no completion stage exists in this mechanism, so nothing is unsatisfiable and no unauthorized effect is produced and no obligation is fabricated — the four admitted cases do execute their declared `internal_write`, and the class is inert under this pair, recorded as such rather than scored as a pass); the four `keyholder_widen` attacks are denied `APC-DENY` because the shadow APC refuses the widened resource and that refusal is signed evidence, not because the token check noticed anything about the minter.

## 10. Arm 7 (`apc_sentinelagent_fail_closed`): refusals and false denials

Observed codes: {"ADMITTED": 36, "SHADOW-DENY": 42, "SIGNATURE_INVALID": 4, "T1-REFUSE:completion_untranslated": 4, "T1-REFUSE:dynamic_state_untranslated": 22}. Zero leaks. 20 benign cases are refused (one per benign case of the five dynamic-state templates: expiry, revocation, composition history, replay/budget ×2 templates), as locked. Attack-side FD events: 4 from `unsatisfiable_verify` (completion_untranslated; oracle-clean once refused) plus 4 from `repeated_calls-0-a`/`-3-a` (two events each). Total FD events 28 vs locked 26; the delta is reconciled in §13 — the lock's derivation enumerated only the first calls, but under the locked FD definition the second calls are also oracle-clean refusals: the refused first call never executes, so the oracle's budget is unchanged, and the shadow APC denies the second call (`SHADOW-DENY`) after charging its own budget on the first approval.

## 13. Discrepancies and reconciliation (post-run; lock and artifacts unmodified)

Two locked counts did not match the observed values. Both are in the lock's derivation text; neither changes any leak, false-denial case, per-case prediction, leak set, or the seam test, and neither was patched after the fact. `results/sa/reconciliation.json` records them mechanically.

1. **Arm-7 FD events: locked 26, observed 28.** The lock's note derived "20 benign dynamic refusals + 4 unsatisfiable_verify-a + 2 oracle-clean first calls of repeated_calls-a". Each affected case produces *two* FD events: the first call is refused as dynamic state (oracle-clean, unexecuted, so the oracle budget never charges) and the second call is then also oracle-clean and is denied by the shadow APC (`SHADOW-DENY`) after the shadow's own budget was charged on the first approval. Observed events: `repeated_calls-0-a` ev0 `T1-REFUSE:dynamic_state_untranslated`, ev1 `SHADOW-DENY`; `repeated_calls-3-a` the same. The locked FD **definition** yields 28; the locked **derivation** undercounted by enumerating first calls only.
2. **Arm-5 confusion TN: locked 68, computed 20.** The lock's confusion block wrote `true_negative: 68` (the safe cases over all 96: 48 benign + 4 resource_widen + 4 recipient + 4 omitted + 4 unsatisfiable + 4 foreign_key = 68), while the metrics code computes TP/FP/FN/TN over the 48 attack cases (TN 20 = the 16 rejected + 4 allowed no-effect). TP/FP/FN are 28/0/0 either way; the counts agree at the count level (28+20=48, 28+68=96). This is a denominator slip in the lock's block, recorded, not edited.

- The marker-bearing confidential payload contents: counted, not reproduced.

## 15. Not claimed

- Not claimed: any vulnerability in SentinelAgent or in APC. The findings are properties of this implementation under our bridge mapping and this key model.
- Not claimed: that these results describe SentinelAgent as deployed. The pinned prototype is an in-process reference implementation; the key constant is ours, and no real DAS infrastructure was involved.
- Not claimed: that the bridge represents the only reasonable cross-mechanism handoff. It is one mapping, locked before the run, with its alternatives recorded.
- Not claimed: that the zero seam test generalizes beyond these three pilots' case families; it is a recorded property of every case we built, not a theorem.
- Not claimed: that arm 6/7's zero leaks are safe remedies in production — arm 6 assumes the attestation is verified under the trusted key and arm 7 accepts 20 benign false denials; both are scoped design choices in the mapping.
- Not claimed: comparability with any published benchmark numbers; the case set is constructed here and the mechanisms' own evaluations are self-reported by their authors.
